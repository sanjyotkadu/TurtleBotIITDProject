01

System block diagram

The whole robot is one signal path. You push a stick on the transmitter; that becomes a radio packet, then a serial frame the Teensy reads, then a math command, then PWM and direction pins, then motion. The wheels' encoders send counts back so the Teensy can (eventually) know how far each wheel turned.

03

Software architecture

The old sketch was one 339-line file. It is now split into small modules, each owning one job and exposing a short API. main.ino is deliberately thin — it only wires the modules together and holds setup() and loop(). The important thing to see is the pipeline: the RC command flows left to right and becomes motion.

ModuleFilesResponsibility
RCControl.h / .cppRead the iBUS link, normalise the sticks, calibrate centres, run the arm/disarm state machine, detect failsafe.
kinematics.h / .cppPure math: turn (Vx, Vy, Ω) into three wheel powers. No hardware.
motorControl.h / .cppTurn a signed power into direction pins + PWM on an L298N channel.
encoder.h / .cppCount quadrature ticks per wheel via interrupts; convert to millimetres.
diagnostics.h / .cppStatus-LED patterns and the serial debug dump.
startupSequence.h / .cppBlocking boot flow: wait for the link, then calibrate.
main.ino.inoWires it all together — setup() and loop() only.
04

Startup sequence

Before the robot is allowed to move, it must be sure the radio link is real. This ordering is deliberate — it is what stopped the motors from twitching on power-up in earlier versions. Nothing arms, and the centres are not measured, until valid iBUS frames are actually arriving.

05

RC control & arming

This module is the robot's connection to you. It reads the FlySky receiver over iBUS — a single-wire serial link where all channels are packed into one 32-byte frame every ~7 ms — and turns the raw stick numbers (roughly 1000–2000) into clean values from −1.0 to +1.0.

What each channel does

0Right stick — left/rightVx · strafecentre ≈ 1474

2Left stick — up/downunusedno spring return

5Aux switchunused—

Normalising a stick

A raw reading is turned into a −1…+1 value relative to its calibrated centre, with a small deadzone (±30 counts) so a stick that rests slightly off-centre still reads as zero. While disarmed, the centre is continuously nudged toward the resting value, so drift can never lock in a false zero.

The arming state machine

Arming is intentionally hard to do by accident. The motors go live only after a fresh flip of the enable switch while every stick is centred. If the link ever drops, everything falls back to failsafe and the motors stop.

06

Kiwi kinematics

A "kiwi" drive has three omni-wheels 120° apart. Because the wheels can slip sideways on their rollers, the robot can move in any direction and spin at the same time — it is holonomic. This module answers one question: given a desired motion (Vx, Vy, Ω), how fast should each wheel spin?

The mixing equations

Each wheel's raw power is just the projection of the motion vector onto that wheel plus the rotation term:

C = −Vx + Ω
A = 0.5·Vx − 0.866·Vy + Ω
B = 0.5·Vx + 0.866·Vy + Ω

0.866 ≈ √3⁄2, from the 120° spacing.

Normalising

If any wheel's number exceeds 1.0, all three are divided by the largest one. That keeps the direction of motion correct while never commanding more than a motor can give — kiwiMix() always returns values in −1…+1.

Wiring correction — kiwiMix() is pure math and does not know how the motors are wired. main.ino multiplies each result by DIR_A_CW / DIR_B_CW / DIR_C_CW (from config) so a positive command always spins the wheel the way the math intends. Fixing Motor C's sign here is what made "left stick spins, right stick strafes" behave correctly.
07

Motor control

The lowest layer. It knows nothing about kinematics or the radio — it just takes one signed number from −1.0 to +1.0 and drives one L298N channel. The sign picks direction; the magnitude becomes PWM duty (scaled to 0–255).

Power commandIN1IN2PWM on ENResult
power > 0HIGHLOW|power| × 255forward
power < 0LOWHIGH|power| × 255reverse
power = 0LOWLOW0stop / coast

stopAllMotors() is simply this with 0.0 on all three wheels — it is called at boot, whenever the robot is not enabled, and on failsafe.

08

Encoders

Each wheel has a two-channel (quadrature) encoder. The two channels are square waves 90° out of phase. Every wheel produces about 2115 counts per revolution, and each count is worth about 0.055 mm of travel at the rim. This module counts those ticks so the robot can measure how far each wheel has turned.

Direction sign is a starting guess. Whether a wheel counts up or down when driven forward depends on how C1/C2 are wired. If a wheel counts the wrong way, swap that motor's C1/C2 wires or flip the sign in its ISR. This module is new — it was scaffolded from the pins and CPR already in the config; nothing read the encoders before.

Diagnostics

You can read the robot's whole state from the onboard LED — no laptop needed. The patterns are checked in priority order, so failsafe always wins.

Serial debug

Ten times a second, the firmware prints a line with the normalised inputs, the raw channel values, the live centres, and each wheel's commanded power and PWM — enough to diagnose almost any movement problem from the serial monitor.

10

The main loop

Everything above comes together here. Each pass reads the radio, decides whether the robot is enabled, updates the LED, and either drives or stops — then prints debug at a throttled rate. This runs hundreds of times a second.

Arm sequence, start to finish: power on → LED slow-blinks until the receiver is found → centre all sticks → LED goes solid ON → flip the enable switch OFF then ON → LED goes solid OFF → armed. Move a stick with the switch already on and nothing happens until you re-flip it.
